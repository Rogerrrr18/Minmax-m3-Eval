# MiniMax-m3 科学评测 v3.0

> 四模型 × 十一维度 × 640 题 · GPT-5.5 独立裁判 · 0-10 分制

---

## 📖 项目介绍

这是一个面向中文大语言模型的**科学横向评测项目**，核心目标是：

1. **客观评估 MiniMax-m3 的真实能力水平**
2. **与 deepseek-v4、mimo-v2.5、kimi-k2.6 等主流模型进行同场对比**
3. **建立可复现、可对比、覆盖全面的中文大模型能力基准**

如果你刚接触这个项目，可以把这里理解为一个"大模型考试系统"：我们准备了 640 道涵盖代码、SQL、数学、办公、NLP 等场景的题目，让 4 个模型分别作答，再由 GPT-5.5 作为"阅卷老师"独立打分。

---

## 🎯 评测意图

市面上的模型宣传往往侧重单一维度（如代码能力或对话能力），而真实业务场景需要模型同时具备：

- **编程开发**：写代码、补全代码、修 bug、做优化
- **数据分析**：写 SQL、做表格处理
- **逻辑推理**：解数学题、算法设计
- **办公协作**：写文档、处理邮件、信息抽取
- **多语言理解**：中英文混合场景下的语义判断

本评测就是围绕这些真实场景设计的，避免"刷榜式"评测，更关注模型在**综合办公 + 代码开发**场景下的实际可用性。

## 🧪 评测方法

整个评测分为 4 个阶段，如下图所示：

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ 1. 数据准备  │ -> │ 2. 模型调用  │ -> │ 3. 自动验证  │ -> │ 4. GPT裁判  │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

### 阶段 1：数据集准备

我们从官方/学术数据集加载题目，对缺失维度通过代码注入、NER 构造、办公场景设计等方式补全。最终形成 **11 个维度、640 道题** 的测试集。

| 维度 | 题目数 | 数据来源 |
|------|--------|----------|
| 代码生成 | 100 | HumanEval 30 + MBPP 40 + BigCodeBench 30 |
| SQL 查询 | 50 | Spider |
| 算法能力 | 80 | GSM8K 50 + MBPP-Algo 30 |
| 代码补全 | 50 | CodeSearchNet |
| 错误修复 | 60 | 自建-BugFix（向正确代码注入常见 bug） |
| 代码优化 | 50 | 自建-Optimize 30 + BigCodeBench-Opt 20 |
| 多语言办公 | 50 | PAWS-X |
| 信息抽取 | 50 | 自建-NER（覆盖科技、金融、医疗、体育等领域） |
| 文档撰写 | 50 | XSum 30 + CCE 20 |
| 邮件处理 | 50 | 邮件评测集 15 + 自建 35 |
| 表格处理 | 50 | 格物评测集 5 + 自建 45 |

### 阶段 2：模型调用

4 个模型分别独立完成全部 640 题：

- **MiniMax-m3**：官方 API（https://api.minimax.chat/v1）
- **deepseek-v4-flash**：通过 opcrouter 代理
- **mimo-v2.5-pro**：通过 opcrouter 代理
- **kimi-k2.6**：通过 opcrouter 代理

调用参数：
- 代码类任务 `max_tokens = 4096`
- 办公/NLP 类任务 `max_tokens = 2048`
- 启用 3 次指数退避重试
- 自动过滤 `<think>` 等思考标签
- 每维度实时保存 checkpoint，支持断点续跑

### 阶段 3：自动验证

对代码/SQL/算法类任务做轻量级规则检查：

- 输出是否为空或 API 错误
- 输出是否被截断
- 是否包含有效的代码/SQL 结构

输出 **0-3 分** 的基础分，作为 GPT 裁判的参考。

### 阶段 4：GPT-5.5 独立裁判评分

这是评测的核心环节。我们对每个模型、每个维度独立调用 GPT-5.5：

- 裁判**不知道**输出对应哪个模型
- 每个维度有专门的评分标准
- 输出 **0-10 分** 和简短评分理由

评分标准示例：
- **代码类**：0-3 = 无法运行；4-5 = 可运行但结果错；6-7 = 基本正确；8-9 = 正确且高效；10 = 完美
- **办公类**：0-3 = 不满足要求；4-5 = 勉强满足；6-7 = 基本满足；8-9 = 很好；10 = 超出预期
- **SQL 类**：重点考察语义正确性、JOIN/HAVING/聚合函数使用
- **NER 类**：重点考察实体边界正确性、是否有幻觉（编造实体）

## 🚀 如何复现评测

### 环境要求

- Node.js >= 18（需要原生 `fetch`）
- Windows / macOS / Linux 均可

### 1. 克隆项目

```bash
git clone https://github.com/Rogerrrr18/Minmax-m3-Eval.git
cd Minmax-m3-Eval
```

### 2. 运行完整评测

```bash
cd 04-脚本工具
node run_all.js
```

这会依次执行：模型调用 -> 自动验证 -> GPT 裁判评分 -> 生成报告。

**注意**：完整跑完需要约 5-6 小时（模型调用 ~4 小时 + 裁判评分 ~2 小时）。

### 3. 只跑单个阶段

```bash
# 只跑模型调用
node eval_v3.js

# 只跑自动验证
node auto_validator.js

# 只跑裁判评分
node judge_v3.js

# 只生成报告
node report_v3.js

# 只生成 HTML 研报
node generate_report_html.js
```

### 4. 并行跑多个模型（加速）

```bash
# 分别启动 4 个模型（可并行）
node eval_v3_single.js MiniMax-m3
node eval_v3_single.js deepseek-v4-flash
node eval_v3_single.js mimo-v2.5-pro
node eval_v3_single.js kimi-k2.6
```

每个模型跑完后会自动保存 checkpoint，支持断点续跑。

## 📊 结果解读

评测完成后，最重要的文件是：

| 文件 | 内容 | 用途 |
|------|------|------|
| `eval_report_v3_research.html` | 完整 HTML 研报 | 直接浏览器打开查看 |
| `eval_report_v3.json` | 结构化数据 | 用于二次分析或可视化 |
| `eval_report_v3.md` | Markdown 简版 | 快速浏览 |

### 如何看懂得分

- **综合得分**：模型在 640 题上的平均分（满分 10 分）
- **维度得分**：该维度所有题目的平均分
- **健康率**：非空且未被截断的输出比例
- **低分数量**：得分 ≤3 的题目数量，反映"硬伤"数量

### 当前最佳结果（v3.0）

| 排名 | 模型 | 综合得分 |
|------|------|----------|
| 1 | deepseek-v4-flash | 7.92/10 |
| 2 | mimo-v2.5-pro | 7.83/10 |
| 3 | **MiniMax-m3** | **7.82/10** |
| 4 | kimi-k2.6 | 7.56/10 |

MiniMax-m3 的优势维度：**算法能力**、**信息抽取**、**代码优化**。  
主要短板：**代码补全**（建议优先优化）。

## 🔧 常见问题

**Q：为什么代码补全维度全模型得分都很低？**  
A：当前 prompt 要求模型"补全缺失代码"，但模型往往输出完整函数。这是一个测试方式设计问题，后续版本会优化。

**Q：为什么 SQL 查询得分普遍不高？**  
A：Spider 数据集包含多表 JOIN、聚合、子查询等复杂场景，对 schema 理解要求较高。

**Q：评测结果会随 GPT-5.5 的随机性波动吗？**  
A：已设置 `temperature=0.1`，随机性较低。但不同裁判模型或不同评分标准仍可能产生差异。

**Q：如何添加新模型进行对比？**  
A：在 `eval_v3.js` 或 `eval_v3_single.js` 的 `MODELS` 数组中添加模型配置即可。
