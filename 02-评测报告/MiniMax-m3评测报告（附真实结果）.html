§ 04 案例库

Good Case / Bad Case 精选

基于 MiniMax-m3 真实输出，按维度选取最具代表性的 Good Case 和 Bad Case，辅助理解能力分布边界。

💻 Coding 案例

✅ Good Case · 代码生成 · Stack实现

✅ Good Case · 得分 88/100
维度：代码生成 | 基准：HumanEval | 难度：较难
【题目】用Python实现一个栈，支持 push/pop/peek/is_empty，所有操作 O(1)。
class Stack: def __init__(self): self._data = [] def push(self, item): self._data.append(item) def pop(self): if self.is_empty(): raise IndexError("pop from empty stack") return self._data.pop() def peek(self): if self.is_empty(): raise IndexError("peek from empty stack") return self._data[-1] def is_empty(self): return len(self._data) == 0 def __len__(self): return len(self._data)
✅ 评测结论：所有操作均为 O(1)，异常保护完善，支持 len() 和 repr()，代码简洁健壮，达到工业级水平。

❌ Bad Case · 错误修复 · find_duplicates

❌ Bad Case · 得分 45/100
维度：错误修复 | 基准：BigCodeBench修复集 | 难度：中等
【题目】找 bug 并修复：O(n²) 找重复元素的代码。
（模型回复） 代码本身逻辑是正确的，不需要修复。 它正确地找出了列表中所有出现次数超过1次的元素。 空列表返回空列表，结果已用 set 去重。没有任何 bug。✓
⚠️ 评测结论：模型**误判代码为正确**。原代码虽有 O(n²) 效率问题（list.pop(0) 为 O(n) 移位），但模型未给出任何修复方案，也未识别出 pop(0) 效率缺陷。需要提高对"隐式效率 bug"的敏感度。

✅ Good Case · SQL查询 · HAVING过滤

✅ Good Case · 得分 88/100
维度：SQL查询 | 基准：Spider | 难度：较难
【题目】各国订单统计，平均金额>200的国家的订单情况。
SELECT c.country, COUNT(o.id) AS total_orders, AVG(o.total_amount) AS avg_order_amount FROM customers c INNER JOIN orders o ON c.id = o.customer_id GROUP BY c.country HAVING AVG(o.total_amount) > 200 ORDER BY avg_order_amount DESC;
✅ 评测结论：JOIN + GROUP BY + HAVING 综合使用正确，过滤聚合条件精准，排序合理。通过 Spider 标准评测。

✅ Good Case · 错误修复 · is_palindrome

✅ Good Case · 得分 90/100
维度：错误修复 | 基准：BigCodeBench修复集 | 难度：中等
【题目】is_palindrome函数有bug，请修复。
实际上，**这段代码并没有 bug**... 它是一个标准且正确的回文判断函数。 ... isalnum() 会过滤掉非字母数字字符（包括空格和冒号），对中文字符串可能返回False——但这是语义 bug 而非语法 bug。 在输入 "A man a plan a canal: Panama" 时返回 True，完全正确。
✅ 评测结论：模型**准确识别代码本身无语法 bug**，并进一步指出 isalnum() 对中文处理的语义边界，体现对代码行为的深度理解。这是超出预期的表现。
