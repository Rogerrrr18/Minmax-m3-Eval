1.3 评测流程

1

数据集准备

从官方/学术数据集加载题目，对每个维度保证 ≥50 题。缺失部分通过代码注入、NER 构造、办公场景设计等方式补全。

2

模型调用

每个模型独立完成全部 640 题。代码类任务 max_tokens=4096，办公/NLP 类 max_tokens=2048；启用 3 次指数退避重试，过滤 think 标签，实时保存 checkpoint。

3

自动验证

对代码/SQL/算法类任务做规则级检查（非空、截断、代码结构），输出 0-3 基础分。深度评分由 LLM 裁判完成。

4

GPT-5.5 独立裁判评分

逐模型独立调用 GPT-5.5，按维度专门评分标准给出 0-10 分及理由。裁判不知道输出对应哪个模型，避免位置偏见。

1.4 评分标准

采用 0-10 分制，不同维度有专门评分标准：

  • 代码类（生成/补全/修复/优化/算法）：0-3 分=无法运行或严重错误；4-5 分=可运行但结果有误；6-7 分=基本正确但效率或风格有瑕疵；8-9 分=正确且较高效；10 分=完美实现。
  • SQL 查询：重点考察语义正确性、JOIN/HAVING/聚合函数使用。
  • 办公类（文档/邮件/表格/多语言）：0-3 分=不满足要求；4-5 分=勉强满足；6-7 分=基本满足；8-9 分=很好；10 分=超出预期。
  • NLP 类（信息抽取）：重点考察实体边界正确性、是否有幻觉（编造实体）。

关键发现

五、关键发现与讨论

5.1 MiniMax-m3 的优势领域

MiniMax-m3 在 算法能力（9.11/10）、信息抽取（9.18/10）、代码优化（7.92/10） 三个维度取得第一。这说明该模型在逻辑推理、结构化信息理解和代码质量优化方面具有较强竞争力。特别是在 GSM8K 数学题和复杂 NER 任务上，MiniMax 展现出稳定的准确率。

5.2 代码补全是全模型共性问题

四个模型在代码补全维度得分均不理想（MiniMax 1.02、deepseek 2.42、mimo 3.38、kimi 1.16）。分析发现，该维度题目要求模型根据上下文补全缺失代码片段，但模型往往输出完整函数而非仅补全缺失部分，导致裁判评分偏低。这是一个 prompt 设计问题，后续应优化测试方式或放宽评分标准。

5.3 SQL 查询能力普遍偏弱

所有模型 SQL 查询得分集中在 5-6 分区间，显著低于其他代码类维度。这与 Spider 数据集的真实复杂性有关：多表 JOIN、聚合函数、HAVING 子句和日期函数组合对模型的 schema 理解和 SQL 语法掌握提出了较高要求。

5.4 MiniMax 输出稳定性最佳

在 640 次调用中，MiniMax-m3 产生了 0 个空/错误输出，是四模型中稳定性最好的。相比之下 kimi 有 46 个空/错误输出，反映出 kimi 在并行调用过程中存在较高的 API 波动率。

5.5 办公类任务差距较小

文档撰写、邮件处理、表格处理三个维度，四模型得分在 7.6-8.6 之间，头部差距不超过 1 分。这说明通用办公助手能力已相对成熟，各家模型在此领域已形成同质化竞争。

局限与建议

七、局限性与优化建议

7.1 当前局限性

  • 裁判模型（GPT-5.5）本身存在主观性和评分偏好，不同裁判模型可能给出不同结果。
  • 代码补全维度的 prompt 设计可能过于严格，导致全模型低分。
  • 未引入可执行测试（pass@k），代码类任务仍依赖 LLM 主观评分。
  • 办公类任务评分标准较难量化，存在一定的解释空间。

7.2 优化建议

  • 短期重点：修复代码补全能力，优化对不完整代码上下文的理解；针对复杂 SQL 的 JOIN、聚合、子查询做专项优化。
  • 长期方向：巩固算法推理和信息抽取的优势，形成差异化竞争力；降低长代码生成中的截断率；引入代码可执行验证，减少对 LLM 裁判的依赖。
